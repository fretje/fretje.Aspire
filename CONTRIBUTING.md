# Contributing

Thanks for your interest in improving `fretje.Aspire`!

## Getting started

You need the .NET SDK version from [`global.json`](global.json) (newer feature bands are fine).

```sh
dotnet build
dotnet test tests/fretje.Aspire.Hosting.LocalEventing.Tests/fretje.Aspire.Hosting.LocalEventing.Tests.csproj
```

Tests use [xunit.v3](https://xunit.net/) on the [Microsoft Testing Platform](https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro)
(enabled for `dotnet test` through `global.json`). The unit test project is a normal executable, so you can also run it
directly, with filters: `dotnet run --project tests/fretje.Aspire.Hosting.LocalEventing.Tests -- --filter-method "*Nameof*"`.

### Integration tests

`tests/BlobEventGridSample.IntegrationTests` runs the full sample end-to-end. It requires **Docker** — the AppHost
starts Azurite and the Event Grid emulator as containers. Run it explicitly:

```sh
dotnet test tests/BlobEventGridSample.IntegrationTests/BlobEventGridSample.IntegrationTests.csproj -c Release
```

These tests are intentionally excluded from the default CI matrix (which runs on both Ubuntu and Windows) and run in a
dedicated Linux + Docker job on every push/PR. The **Publish** workflow runs the full solution's tests on Ubuntu, where
Docker is available.

## Project layout

- `src/Aspire.Hosting.LocalEventing` - the NuGet package (builder extensions and resources for the local Event Grid
  emulator and the blob storage event proxy).
- `samples/` - a runnable Aspire sample (AppHost + Azure Functions blob EventGrid trigger + a client that uploads a
  blob) demonstrating the whole flow.
- `tests/Aspire.Hosting.LocalEventing.Tests` - unit tests for the package.
- `tests/BlobEventGridSample.IntegrationTests` - end-to-end integration tests for the sample (requires Docker).

## Releasing (maintainers)

**Preview releases** (`v1.0.0-preview.1`): no release-file changes needed, just tag. Do the steps below for the first
stable release.

1. Update `CHANGELOG.md` by turning the **Unreleased** section into the new version (e.g. `## [1.0.0] - YYYY-MM-DD`),
   adding entries under `### Added` / `### Changed` / `### Fixed` as needed. This is a **manual** edit — there is no
   automation that generates or updates the changelog.
2. Merge to `main`, then tag and push:
   ```sh
   git tag v1.0.0
   git push origin v1.0.0
   ```
3. The **Publish** workflow builds, tests, packs, pushes to nuget.org and creates the GitHub release.
   Tags with a suffix (`v1.1.0-preview.1`) are published as pre-releases.

Note: the GitHub release body is generated by `gh release create --generate-notes` (from merged PR titles) and is
independent of `CHANGELOG.md`. Keep them in sync by hand.

The package version comes from the git tag (via [MinVer](https://github.com/adamralph/minver)); there is no
version number to edit in the project files.

One-time setup (nuget.org [Trusted Publishing](https://aka.ms/nuget/trusted-publishing), no API key needed):

1. On nuget.org: user menu → **Trusted Publishing** → add a policy:
   - Package owner: yourself (or your organization)
   - Repository owner: `fretje`, Repository: `fretje.Aspire`
   - Workflow file: `publish.yml` (file name only)
   - Environment: leave empty
   - Scopes: allow publishing **new packages** and **new versions**, glob pattern `fretje.Aspire.Hosting.LocalEventing`
   2. In the GitHub repo: Settings → Variables (repository) → add the variable `NUGET_USER` with your nuget.org
      **profile name** (not your email address).

   A policy for a private GitHub repo is only temporarily active for 7 days until the first successful publish
   (restart the window on the Trusted Publishing page if it lapses). Public repos don't have this limitation.
